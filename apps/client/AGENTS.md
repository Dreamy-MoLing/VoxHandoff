# VoxHandoff client guide

This file inherits the repository-root `AGENTS.md`. Root product and security
invariants remain binding; this file only narrows the rules for
`apps/client/**`.

## Boundaries

- Keep one Flutter client for Windows, Linux, macOS, iOS, and Android. Platform
  directories may contain host integration only; product behavior belongs in
  `lib/` and must not fork by platform without an explicit capability boundary.
- Keep domain models independent from Flutter and generated protobuf types.
  Translate protocol frames in `lib/infrastructure/gateway`, coordinate them in
  `lib/application`, and expose only client-domain state to `lib/presentation`.
- One production owner reads `GatewayLiveConnection.frames`. Route all frames
  through one application frame router, then give its event branch to the
  synchronizer; do not add a second `listen`, `first`, or `drain` consumer that
  can steal or reorder command results, status facts, or events.
- Persist the complete mapped event and its conversation cursor atomically in
  Drift before publishing view state or acknowledging it. Exact duplicates may
  converge; identity, payload, route, or sequence conflicts fail closed.
- Track a request's exact device/conversation/session/Node/Agent route before
  accepting its events. Keep full replies durable even when summary, TTS, STT,
  or playback fails.
- Never automatically drain queued executable commands after startup,
  reconnect, or recovery. Send, interrupt, approval, clarification, deletion,
  publishing, and authorization actions require a current explicit user act;
  an uncertain submission outcome remains visible and is not silently retried.

## Generated files and storage migrations

- `lib/infrastructure/storage/drift_client_event_ledger.g.dart` is generated by
  `build_runner`; never hand-edit it. Regenerate with:

  ```bash
  cd apps/client
  dart run build_runner build
  ```

- A Drift schema change must increment `schemaVersion`, add a forward migration,
  and include upgrade and reopen tests that preserve events, request routes, and
  cursors. Do not use database deletion/recreation as a migration path.
- Generated protocol bindings live under `packages/protocol/dart`; change the
  source proto and use the root protocol generation/check commands instead of
  patching bindings here.

## UI and platform evidence

- Reuse the tokens and restrained visual language in
  `lib/presentation/design/`. Keep state-specific UI in `lib/presentation/` and
  make disconnected, working, awaiting-user, failed, cancelled, and uncertain
  states distinguishable without color alone.
- A material visual-state change needs widget/accessibility coverage and, when
  layout changes, intentional desktop and phone baselines in `test/goldens/`.
- Keep `android/`, `ios/`, `linux/`, `macos/`, and `windows/` buildable. Mobile
  code must never gain local process-launch capabilities; desktop may start only
  the bundled sidecar defined by the root architecture.

## Commands and completion gate

From `apps/client`:

```bash
flutter pub get
dart run build_runner build
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
```

Run a focused test with `flutter test test/<name>_test.dart`. Before handoff, run
`npm run flutter:check` from the repository root; it verifies the pinned Flutter
toolchain, generated Drift file, formatting, analysis, and the full client test
suite. Do not expose real secrets, credentials, confirmed user text, or raw
recordings in logs, diagnostics, fixtures, or golden labels; tests use only
obviously synthetic safe values.
